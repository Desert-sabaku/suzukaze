# 0928：2カメラ方式の成立性の予備検証

続報：[配置・素材を変えない追加検証](0928-multicam-followup.md)。
実演条件の補足と現時点の判断：[引き継ぎ資料](0928-multicam-handoff.md)。
ラムネ・夕涼みはphase説明UIなしで実演されており、以下はその条件での評価記録。

## 結論

**打ち水で視点の相補性を確認した。ただし、既存アプリをそのまま2系統に増やして
安定した4所作認識ができる状態ではない。**

- 人物選択を無効化した全画面解析では、打ち水はcamera1単独2/3、camera2単独2/3、
  どちらかが反応する試行は3/3だった。異なる試行を互いに補っている。
- 同条件で扇ぎは両カメラとも3/3。今回の試行では検出試行数の追加効果はない。
- ラムネは全条件・両カメラとも0/3。視点を増やすだけでは解決していない。
- 夕涼みは全画面camera2で1/3だが、その出力は約0.20秒しか続かない。
  これを実用的な成功とは扱わない。
- 既存の人物選択を有効にするとcamera2は4所作とも0/3。
  画角に合わない人物選択・マスク条件の影響が大きい。
- 全画面解析には打ち水の注釈区間に対応しないイベントがcamera1で23件、camera2で9件ある。
  単純なOR統合を採用できる結果ではない。

生データ：[推論・試行評価](../shared/results/0928-multicam-results.json)、[集計・原因診断](../shared/results/0928-multicam-diagnostics.json)。

## 対象と方法

- 入力：`shared/videos/0928/` の13テイク、26動画、計5,586フレーム。
- camera1：左側のInsta360 Link 2C。camera2：右側のLogicool HD Webcam C615。
- 全動画を3条件で再生し、計16,758フレームをMediaPipe Lite VIDEOモードへ入力。
- 成績集計：両カメラにaction注釈がある12テイク。扇ぎ・打ち水・ラムネ・夕涼み各3試行。
  `002011` はaction区間がなく、成功率・誤反応集計から除外した。
- 動画SHA-256と注釈の参照SHA-256、保存・注釈・動画の総フレーム数を照合。
  全動画を末尾まで実際にデコードして確認した。
- 0928データでの学習・閾値調整は行っていない。

| 条件 | 入力と判定 |
| --- | --- |
| `rules_full` | 全画面、人物選択なし、既存ルール判定。視点の相補性を調べる診断条件 |
| `rules_subject` | 既存の人物選択あり、既存ルール判定。初期探索時は既存の中央マスク |
| `learned` | 0924学習済みラムネモデル、既存の横幅35〜75%マスク。その他の所作判定も同じマスク後の骨格を使用 |

扇ぎ・夕涼みはaction区間内に1フレーム以上その表示状態が出れば「反応あり」。
打ち水・ラムネはaction区間内に`occurrences`のイベントが出た場合のみ「反応あり」とした。
保持表示を開栓の繰り返しと数えない。ラムネはOPENED注釈区間内のイベントも別集計した。
今回、ラムネはaction内・OPENED内ともすべて0だった。

**この試行単位の指標は緩い。** 打ち水の正確な放水時刻、扇ぎ・夕涼みの安定した表示を
保証しない。JSONには初回反応までの時間、別ラベル出力時間、区間外イベント数も保存した。
初回反応時間は準備を含むaction開始から測っており、成功動作からの遅延ではない。

## 時間軸

全動画は30fpsとして保存されているが、camera2の保存枚数は全テイクで実時間あたり約10枚/秒。
例：`001702` は12.332秒のセッションに対してcamera1が370枚、camera2が124枚。
実デコードでもこの枚数と一致し、camera2最終フレームのコンテナ時刻は約4.10秒だった。
単なる注釈ツールの総フレーム数表示の問題ではない。

推論時刻は各テイク・カメラごとに次で補正した。

```text
effective_fps = decoded_frames / session.duration_seconds
timestamp = frame_id / effective_fps
```

camera1もテイクによって約27fpsの保存ペースになっているので同様に補正した。
動画と注釈自体は変更せず、評価時にフレーム番号から換算している。

これは**均等に撮影されたという近似**である。フレームごとの取得時刻がないので、
途中の停止・不均等な欠落・開始オフセットは復元できない。
補正後の両カメラのaction注釈境界差は最大約0.54秒。
特に`001754`と`001828`の終端差はそれぞれ約0.54秒・0.51秒ある。
注釈の曖昧さも含むため、この差を同期誤差そのものと解釈しない。
代表フレームの横並び画像でも同時刻の細かな姿勢は完全には一致しない。

したがって今回の主評価は、各カメラを自身の注釈で採点して同じテイク単位で比較した。
精密な座標融合・イベント時刻の一致判定は行っていない。

## 誤反応候補

12テイク全体で、同ラベルのaction区間内に対応しないイベント数：

| 条件 | camera1 打ち水 | camera2 打ち水 | camera1 ラムネ | camera2 ラムネ |
| --- | ---: | ---: | ---: | ---: |
| rules_full | 23 | 9 | 0 | 0 |
| rules_subject | 2 | 1 | 0 | 0 |
| learned | 17 | 5 | 3 | 0 |

これには別の所作中の反応と注釈のない準備・復帰中の反応の両方が含まれる。
未注釈区間は正解NONEと確認済みではないので、全件を確定した誤検出とは呼ばない。
ただし、例えばrules_full/camera1の夕涼み`001925`には区間内の打ち水イベントがある。
見逃しを減らすために全反応をOR採用する方式には、明確な懸念がある。

action内で検出できた打ち水は各カメラ1イベントずつで、同一action内の余分な発火は0。
これはカメラ間の二重通知を処理した結果ではない。

## 原因の切り分け

### 人物選択・中央マスクと今回の画角が合っていない

12テイクの全フレームで、認識器へ骨格が渡った割合：

| 条件 | camera1 | camera2 |
| --- | ---: | ---: |
| rules_full | 87.1% | 92.2% |
| rules_subject | 46.4% | 5.0% |
| learned | 75.3% | 39.7% |

これは骨格の正確さではなく、欠落の程度を表す。
代表画像では実演者が大きく映り、頭部や下半身が切れている。
camera2では実演者が左側寄りで、固定の横幅35〜75%マスクが身体の一部を隠す配置になっている。
人物選択には胴体の可視性・位置・時間的な連続性の条件もあるため、
マスクだけを唯一の原因と断定はしないが、全画面との条件差は大きい。

### ラムネは骨格検出だけの問題ではない

rules_full/camera2では3試行とも、action区間の全フレームで骨格が得られ、READYにも到達した。
それでもOPENEDに到達しなかった。`001828`ではcamera1もREADYまで到達している。
一方、`001839`のcamera1は必要6点のvisibilityがすべて0.5を超える割合が23.3%しかない。
視点で構えの取得が改善する例はあるが、既存の押し込み・手の安定条件まで成立していない。

learnedは今回のラムネ区間でほぼIDLEのままで、0924の学習済み構成をそのまま
別画角へ移した際の汎化を確認できなかった。

### 夕涼みは「骨格が出ているのに静止しない」

rules_full/camera1では夕涼み3試行ともaction中の骨格取得率100%・必要6点の可視率100%。
しかし保存骨格を既存の静止判定へ再生すると、速度が計算できた全フレームで
速度しきい値を超え、静止時間が積み上がらなかった。
実動作と推定点の揺れのどちらがどれだけ寄与するかは追加確認が必要。

camera2の`001913`だけ約0.20秒のRELAXING出力があるが、
低いサンプリング頻度も速度判定に影響しうる。これを純粋な視点改善と断定しない。

## 次の検証で優先すること

1. **カメラ別に人物領域を合わせる。** 実演者と両手の動作範囲を含む領域を使い、
   固定中央マスクによる欠落を減らす。今回の画像で試作できる。
2. **ラムネのREADY後の失敗理由と、夕涼みの速度超過点を可視化する。**
   両視点の骨格と判定条件を並べ、手の遮蔽なのか、推定の揺れなのか、
   判定条件と実演の不一致なのかを絞る。
3. **打ち水の区間外イベントを減らしてから統合を比較する。**
   単純ORではなく、カメラ別品質による選択と同一動作の二重通知抑制が必要。
   精密な同期なしでもまずテイク単位の比較を継続できる。
4. 次の撮影では頭・肩・腰・手の全可動域が入る距離を確保する。
   camera2の実取得FPSと保存FPSを一致させ、可能なら取得時刻も残す。

結論の範囲はこの実演者・配置・各3試行に限る。カメラ機種の優劣や
2カメラ方式全般の限界を示す結果ではない。ライブ処理の遅延やキュー落ちは未評価。
